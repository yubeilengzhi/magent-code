# 中文 Code Review

## 沟通原则

- 用建议性语气，不是命令（"建议改成 X" 而不是 "改成 X"）
- 解释 **为什么**，不只是 **改什么**
- 赞赏好的改动（"这个抽象很优雅"）
- 对事不对人（评论代码，不评论人）

## 分级标注

用前缀标识评论的重要性：

| 前缀 | 含义 | 处理 |
|------|------|------|
| `// 阻塞:` | 必须修复才能 merge | ✅ 必须处理 |
| `// 建议:` | 强烈推荐改 | ⚠️ 建议处理 |
| `// 想法:` | 可以考虑 | 💭 自由选择 |
| `// 疑问:` | 我不理解 | ❓ 解释清楚 |
| `// 表扬:` | 好代码 | 👏 学习 |

## 话术模板

### ✅ 推荐

```
// 建议: 这里可以用 early return 减少嵌套
// 解释：当前嵌套 4 层，扁平化后更易读

// 疑问: 这里的边界条件处理了吗？
// 例子：如果 user.name 是空字符串会怎样？

// 表扬: 这个抽象很优雅，把 N 个 case 合并了
```

### ❌ 避免

```
// 改成 X
// 不对
// 这里错了
// 怎么写的？
```

## 国内团队常见反模式

- ❌ **直接 push 到 main**（绕过 review）
- ❌ **"已经测过了"但实际没测**（口头验证）
- ❌ **长时间不合并的 feature 分支**（合并冲突）
- ❌ **PR 描述写 "fix"**（没说明改了什么）
- ❌ **review 只说 "改成 X"**（不说为什么）
- ❌ **维护者高高在上**（review 像审判）
- ❌ **永远说 "稍后再改"**（技术债累积）

## 处理冲突

- ✅ **先理解对方观点**：也许有我没看到的考虑
- ✅ **回到事实**：测试结果、数据、需求
- ✅ **升级第三方**：找资深同事仲裁
- ❌ **争论不休**：浪费时间
- ❌ **暗地里合并**：破坏信任

## 自我反思

- 我是否在用情绪化语言？
- 我是否在评论人而不是代码？
- 我的评论是否有建设性？
- 我给的建议是否具体可执行？

## Anti-Pattern

- ❌ "这段代码是垃圾"（人身攻击）
- ❌ "我以前这么写过"（appeal to authority）
- ❌ 不给替代方案（只说"不对"）
- ❌ 公开批评（私下说更好）
- ❌ 滥用 "nit:"（过度挑剔）

## Checklist

- [ ] 评论是关于代码，不是关于人
- [ ] 给了具体建议
- [ ] 解释了为什么
- [ ] 分级标注（阻塞/建议/想法）
- [ ] 包含赞赏（如果有好的部分）
- [ ] 不滥用 emoji（不要全是 🔥）
